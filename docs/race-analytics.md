# Race analysis

The viewer uses recorded frames, result records and events. `src/data/analytics.ts` exposes summaries, sampled lead gaps and ranks, HP changes, acceleration, status intervals, and skill activation rows. `scripts/analyze-race.ts` runs the same analysis offline:

```powershell
node --import tsx scripts/analyze-race.ts race.json analysis.json
```

Analysis stops at each runner's simulation finish time. Display finish time is kept separately. HP totals are sums of observed decreases/increases, including an interpolated final boundary when available; they are not a calculation of base consumption, skill recovery or causal damage. Lead gaps use the complete field and remain unknown when a runner's distance is missing. The winner is the runner whose recorded `finishOrder` is 1. In-race places use that result after each finish time, and distance order before it; equal distances do not become a shared place. Skill conditions still keep a position range when two sampled distances are exactly equal, because a single rank predicate is not proven. Last-spurt time is interpolated at the recorded last-spurt distance.

`summary.spurtSpeed` interpolates recorded speed at that spurt crossing. `summary.finishGapDistance` is the recorded winner's distance minus each runner's distance at the winner's raw simulation finish time, using interpolation only when the complete field is available. Neither replaces the recorded finish-time gap. A causal spurt speed gain is omitted because a verifiable counterfactual baseline is unavailable.

Rushed modes and front blocking are recorded in the Global frame layout. Their interval boundaries have the frame sampling precision. Incomplete intervals retain an unknown end and a last observed boundary. Spot struggle, dueling and the other runner-local event types have recorded starts; this layout does not provide their ends. Reference downhill grades establish downhill sections, not downhill mode activation. Pace modes are not identified from acceleration alone.

Modeled candidates retain `evidence="estimated"` in the analysis. Presentation uses concise PU, PD, SS, DH and Dueling labels, with modeled provenance in details and dashed graph spans. Baseline pace/downhill candidates require an identified matching course, recorded finish time, complete stats/mood, known distance/strategy aptitudes and ground code. Downhill mode requires downhill geometry and independent normalized HP drain below half the self-speed reference rate; a speed surplus alone cannot identify it. Resolved current-speed effects are removed from actual velocity while active; resolved target-speed/acceleration skills can coexist because their effect on self speed is already observed. Shared skill timing bounds overlapping effects, and instantaneous HP events exclude only their touching sample brackets, regardless of a spare replay duration. Unknown passive scaling, rushed/competition state, effect timing/scaling and foreign recipient masks still withhold affected inference. Pace candidates normalize resolved skill offsets; blocking, start dash, ambiguous skill boundaries and unknown windows stay unassessed. Front SU/OT use distinct compatible lead/rival rules, and nonfront pacemaker selection remains a gap proxy. These reference models retain legal/source attribution in documentation and comments; they do not reproduce every simulator heuristic or prove native state. An absent candidate never establishes mode off. See [downhill inference](downhill-inference.md) and [pace inference and whole-file checks](pace-inference.md).

Spot-struggle estimated duration follows `sqrt(700 × raw guts) × 0.012 × front aptitude`, capped at an observed 9/24-distance crossing and recording/finish. It requires distance, guts and front aptitude but does not require a known venue. Its recorded interval keeps an unknown end; `estimatedEnd` and a separate model interval carry the estimate. Dueling's endpoint subset uses HP below 5% of initial HP, ≥5 m separation from every other recorded dueler, or recording/finish. Missing opponent distances cannot establish separation. These endpoints require recorded HP/positions rather than complete baseline speed inputs. Speed-based/uphill-resume exits remain unresolved, so duration can be an upper estimate. Speed bonuses use replay reference's adjusted-guts formulas and are omitted when mood/category/passive scaling inputs are unknown. The 0.4 downhill, 0.6 pace-down and isolated 1.4 normal/3.5 runaway spot-struggle HP factors are baseline model multipliers, also documented in [Umalator's HP policy](https://github.com/TheCing/uma-tools/blob/5ce95905fef753a33f7519b5559a86e92f5d56cc/uma-skill-tools/HpPolicy.ts). Overlapping rushed spot struggle has a separate 3.6 normal/7.7 runaway factor; the displayed isolated factor does not include it. Dueling has no independent multiplier in that policy; its additional speed affects the HP reference curve. Observed net HP rates and the baseline model rates are exposed separately; no interval is treated as proof of causal HP loss or recovery.

For skill events after time zero, a positive third parameter reports duration in units of 1/10000 second. Missing or zero reported times can use a supported distance-scaled reference duration in separate effective timing fields; failed -1 events are excluded and instant HP effects have zero effective duration. Time-zero activations have an unknown observed end. Parameter four selects the reference condition branch; parameter five is preserved as a target bitmask for the first 32 simulation slots. Reference effects are definitions, not measured effect magnitudes or proof that an HP/speed change came from that skill. Original event parameters round-trip in portable JSON.

Master value/time usage `1` represents the ordinary reference coefficient. Other usage values require special conditional or scaling logic; they are displayed as unresolved reference values rather than fixed effect magnitudes or durations. Ordinary positive base times can show the distance-scaled reference model separately from reported timing. Negative reference base times are passive/no-timed-expiry definitions. Public skill descriptions are available through `getSkillDescription`.

All acquired skills and all recorded proc IDs appear in per-runner skill cards. `activationCount` and `activations` remain recorded-only. `effectiveActive` also includes equipped guaranteed negative-duration passives whose static conditions are proven; these receive the same green styling as recorded procs, without a separate Passive badge or a fake activation time. Wet Conditions requires ground code 2/3/4; Late Surger Savvy requires recorded style 3. Known incompatible settings produce **Conditions unmet**. Supported phase, distance, order and course predicates are evaluated across the entire retained replay, with preconditions allowed to occur earlier. Qualifying samples produce **Conditions met · proc unresolved**; a sampled miss, unsupported random predicate or continuous-time counter does not prove failure. The final-corner flag remains true into the final straight. `post_number` is the starting bracket derived from recorded `frame_order` and field size. Eight or fewer starters keep one horse per bracket. Larger fields place the extra horses in the outer brackets.

Wit outcomes have two bounded reference-evidence paths. A .NET-style RNG reconstruction is accepted only when one stream offset matches every runner's recorded float32 start delay, equipped inventories and `activate_lot` flags are complete, and known recorded procs do not contradict it. Foreign character uniques are normalized to their inherited definition using the recorded outfit before counting lottery draws; an unknown outfit prevents alignment. The output exposes model rolls, threshold, matching runner count and offset. Separately, Concentration's `always==1` branch with an isolated 0.4 gate-delay multiplier can support a failed wit lottery when the recorded delay exceeds its whole activated range and every equipped definition is known with no other gate modifier/override. This path exposes no invented RNG roll. Neither path is a direct observation of server RNG execution. Otherwise met conditions retain an unresolved wit outcome. Raw wisdom/guts order and defeat flags remain uninterpreted.

Runaway is movement style 5 in the simulator. Captured style 1 plus recorded or conditions-proven passive 202051 derives effective Runaway for models/icons, while portable JSON preserves the original selection. It uses its own speed coefficients and the runner's Front aptitude. The short labels SU and OT distinguish their speed up/overtake modes from non-front PU and PD.

Each supported status window exposes concurrent observed travel, sampled HP decreases and recoveries separately from modeled extra distance/HP. Model distance integrates reference target-speed bonus; acceleration, caps and unresolved exits can change actual gained ground. The HP counterfactual removes resolved current-speed skill modifiers from actual observed speed, then removes the modeled status bonus from self speed, known ground and late-guts factors, and compound rushed/spot factors (Front 3.6, Runaway 7.7). These are conditional model values, not observed causal loss. Unknown relevant stat passives suppress baseline estimates instead of contributing zero; a multiplier without a known absolute speed bonus also stays unknown. Same-kind overlapping windows use union duration and withhold numeric totals rather than double-counting. Totals across different overlapping kinds must not be summed as independent gains/costs. See [skill/status evidence and limitations](skill-status-evidence.md) and [condition coverage / capture inputs](condition-coverage.md).

Rushed distance is the recorded speed above the ordinary strategy target, capped at 4% of that target, for every recorded temptation mode. It is integrated before broad pace-inference eligibility, using only inputs required by the current phase. An unresolved speed passive does not erase an early/middle-phase bonus; late-phase calculations still require the relevant speed input. A recorded spurt start does not reveal the HP-selected target, so a window that reaches that spurt stays withheld. Blocked samples and speed still below the ordinary target contribute nothing; a climb toward the 4% contributes only the surplus already reached. Uphill lowers the ordinary target. Positive current-speed and target-skill offsets are removed before the comparison. Section-wit stays separate. The 4% applies to the base strategy target, before terrain, following the pinned position-keep ordering; replay reference's after-uphill ordering differs. The resulting area and HP counterfactual remain conditional reference values rather than observed causal contributions.

The velocity graph has a shared Speed, HP and Gap readout, with separate scales. PU/PD/SU/OT/SS/DH/Dueling/Blocked/Exhausted spans all refer to the selected runner. Course bands are followed directly by clickable skill timing rows. Shared presentation helpers suppress duplicate recorded-start/model rows without changing the underlying analysis evidence.

Race results include **Outer corners**: conditional curvature-only extra metres relative to lane 0, plus equivalent seconds at recorded actual speed. It uses the game path's heading changes and the stated 11.25 m decoded-lane scale, never display-normalized width. Missing path/lane/velocity history withholds complete totals and labels assessed portions. This is a reference-path comparison, not exact causal finish-time loss; lateral weaving, body clearance and changed decisions are excluded. See [corner path method and evidence](corner-path.md). Exhaustion's recorded zero-HP onset and supported equivalent added-time range appear under Last spurt; telemetry retains its selected-runner Exhausted span.

Blocked-loss coverage includes the sampled exit bracket used by telemetry. When the front-block identity changes between samples, that bracket remains unassessed instead of disappearing from the denominator. Supported lost travel includes resolved speed and acceleration skills; their individual foregone benefits are subsets, not amounts to add again to the blocking total.

## Course identity

Initial stat/HP decomposition, useful skill duration, incoming debuff contributions and hill/power comparisons are documented in [effect models and whole-process verification](effect-models.md). Their assessed subsets and conditional reference values remain distinct from recorded timing and concurrent telemetry.

The selected-runner panel shows base stats followed by an effective starting-stat row. The row uses the same decomposition as analysis: mood, initial green skills, course thresholds, ground, style aptitude and applicable caps/bonuses. Hover text lists adjustments; missing required inputs remain unavailable instead of showing a partial sum as the effective total.

Explicit `race_course_set`/horseACT backing fields and course ID aliases take precedence. A `race_instance_id` maps through the installed public master tables `race_instance.race_id → race.course_set`. The extractor includes a small source lookup for offline imports and the same mapping in the downloadable metadata snapshot. A single-race filename beginning with `<race_instance_id>_` can supply the mapping, with separate filename provenance. A conflicting finish distance prevents that filename fallback.

When the course ID is absent, finish distance can be derived by interpolating runner distance at recorded simulation finish times. The estimate is accepted only when all available finish observations are within five metres of the same hundred-metre distance. Post-finish runout never becomes race distance. Distance alone does not identify a venue. Manual course choices persist in portable JSON with `courseIdentity.source="manual"`.

`inferCourse(race, reference)` can narrow matching-distance courses using successful recorded skill events with an explicitly selected master branch. It evaluates necessary track, turn, surface and distance predicates using three-valued logic; an unknown OR alternative remains possible. For ordinary self effects, supported corner conditions use the entire surrounding recorded distance bracket, with a two-metre boundary margin, rather than treating an interpolated position as exact. Owned skills and missing procs provide no positive course evidence. A common venue can be inferred while course/surface remains ambiguous; only one remaining course supplies a course ID. Conflicting evidence supplies no ID. The captured race stays unchanged; an inferred analysis/export choice carries `courseIdentity.source="skill-conditions"` and an **Inferred** label, separately from recorded IDs and manual choices.

Race categories captured from recognized API endpoint groups retain `categorySource="endpoint"`; these are independent of course inference. Static negative skill checks can also use known numeric weather, ground-condition and season codes. Unknown or legacy text values remain unknown.

Calendar guesses and first-distance-match fallbacks are not decoded course identifiers. The viewer does not silently treat either as a recorded course.

### Where the game declares course context

Static declarations in the installed Global IL2CPP v31 metadata identify public `race_instance_id` fields beside replay/context fields. The inspected metadata is 33,532,564 bytes, SHA-256 `27b8f59d91c2be040bba33964ccb6bab37d5ae674b47dfccc32d5793f76edb5f`. Offsets below locate metadata field records, not native object memory or executable instructions.

| Declared type | Field evidence / metadata byte offset |
| --- | --- |
| `ChampionsRoomInfo` | `race_instance_id` 24,835,840; `race_scenario` 24,835,900 |
| `PracticeRaceRaceStartRequest` | `race_instance_id` 24,798,148 |
| `RaceResultInfo` | `race_instance_id` 24,847,348; `race_scenario` 24,847,420 |
| `RoomMatchSavedRoomInfo` | `race_instance_id` 24,848,776 |
| `RoomMatchGetSavedRaceResultResponse.CommonResponse` | Sibling `race_result` 24,802,144 and `race_scenario` 24,802,156 |

The same metadata declares `PracticeRaceApiHelper.CreateRaceInfo(RaceResultInfo, trainedCharaArray, entryInfoArray, onSuccess)` at method-record offset 10,031,516. `RaceInfo`'s constructor at 10,487,996 accepts `raceInstanceId`, `randomSeed`, `RaceType`, season, weather and ground condition; its `RaceCourseSet`, `SimDataBase64` and `SimData` fields are separate. `WorkRoomMatchData.RoomData` constructors accept live `RoomMatchRoomInfo` at 8,545,832 or saved `RoomMatchSavedRoomInfo` at 8,545,904, and declare `GetMasterRaceCourseSet` at 8,546,336. These interfaces support course context being supplied separately from the binary replay; they do not expose the native method bodies or prove the call sequence.

Native inspection of `GameAssembly` (SHA-256 `fe5b71c7d6043e36d1058a210a886bb5ef175da434ba2e615f3a4006397bd44d`) recovered loader stubs but no replay-method body. The Ghidra overview recognized only 27 procedures; that coverage cannot establish a complete runtime call trace. The usable evidence here is the declared interface/context structure and public master mapping.

The collector retains allowlisted public race-instance IDs and maps them through the public master tables. For the saved-room response shape, it lifts only finite numeric race fields from a bounded literal `race_result` object beside its own `race_scenario`; room/player identifiers and runner arrays are excluded. It does not borrow context from another response, race array or history. Earlier collector versions omitted `race_instance_id` from the race-number allowlist, so that field would have been dropped if returned. An older sanitized capture cannot establish which context fields were originally populated. These declarations establish available fields; they do not establish native method execution, exact serializer behavior or server population on every replay route.

## Sources and validation

### Accuracy review, October 2026

The current audit fixes three missing-data paths: unknown active vision branches
no longer silently use base vision; downhill speed fitting rejects unresolved
active movement effects; and short pace/downhill gaps are joined only when the
intervening replay and skill context is readable. Recovery-censored downhill gaps
remain separate. Final-spurt plateau fitting also excludes middle-leg samples,
even if an imported replay has an early spurt marker.

Training, win and fan-count bonuses retain the configured maximum-tier fallback
when those capture inputs are absent. Their explanations now state that
assumption. This is not recovered account history. Whole-file workflows cover
these cases and preserve the original capture bytes.

Remaining accuracy limits are structural: sampled speeds do not uniquely recover
hidden mode decisions or random draws, and replay-context counterfactuals hold
the other runners and race timeline fixed. Condition-key coverage is not proof
that every native condition or causal finish-time effect has been reproduced.
See [performance measurements](performance.md) for output-equivalence checks on
the replay optimization.

Binary strides, event enums, skill parameters and course resolution follow the supported replay layouts. Adapted helpers retain their [MIT notice](../src/data/THIRD_PARTY_LICENSE.txt). Public skill definitions, descriptions, lottery flags and race-instance mappings come from selected read-only master tables. No account/session data is included.

`npm test` exercises the actual sanitizer, import CLI, analytics CLI and JSON reimport as whole processes using synthetic encoded and normalized replays. It checks Kyoto inner/outer mappings, filename provenance, finish distance versus runout, sampled statuses, reported proc timing, HP totals, incompatible static conditions, unknown proc causes and persistent manual course selection. It also checks interpolated spurt speed, nonzero winner-time distance gaps and missing-field results. A model workflow checks pace/downhill candidates, separate competition estimates without a known venue, dueling self/opponent resolution, unchanged observed totals, and suppression when aptitudes or effect-recipient evidence are missing. A course-inference workflow checks selected branches, unknown/failed procs, ambiguous geometry boundaries, OR predicates, conflicting evidence and portable inferred provenance. Existing capture inspection stays local and is never a published test fixture.

Before publishing a viewer change, verify this workflow:

- Run `npm test` and `npm run build`; retain the process results rather than relying on visual appearance alone.
- Import a synthetic race, select runners, seek/play, open skill details, inspect statuses and compare telemetry/results. Check unknown values, dashed modeled spans and provenance details in both themes and a narrow viewport.
- Export and reimport JSON; verify manual course provenance and recorded event parameters survive.
- Check the zoomed replay and local clip preview/download with supported browser encoding.
- Run `python desktop/generate_manifest.py --check` and `python scripts/audit-public-files.py`. After staging the intended files, repeat the audit with `--staged`.

The public-file audit inspects the intended Git inventory for private/generated paths, credentials, key material, personal machine paths and SIDs without printing matched values. Public reference IDs are game definitions; captures, private libraries, investigation output and screenshots stay outside the inventory. Replay fixtures used by these workflows are explicitly synthetic.
